### 0.2 第六部分重建结论

**结论：缺失的第六部分 = 「成片与发布」子系统（对应原文 §1.1 的 ⑤）。** 本规格书按此重建，命名为 `§06 成片与发布`。

**重建依据（三条独立证据，互相印证）**

1. **编号与子系统严格对齐**：原文 §1.1 列出五大子系统 ①智能体脚手架 ②CosyVoice3配音 ③三层模板渲染 ④任务队列 ⑤成片与发布；而第二/三/四/五部分恰好逐一对应 ①②③④ —— 故第六部分必然对应 **⑤成片与发布**。

#### 0.5.2 渲染范围收敛（D2 + D5 · 影响最大）

**v3.0 的渲染设计**（三层模板 → 场景编排 → 逐场景合成 → 合流）**相对口述需求过重**。v3.1 按"一期从简、二期扩展"重构：

| 能力 | 一期（**P0 · 本期必做**） | 二期（P1 · 可选扩展） |
| --- | --- | --- |
| 渲染形态 | **单遍合成**（1 次 ffmpeg 调用） | 三层模板场景编排 |
| 输入 | 跑酷素材 + `voice_master.wav` + 水印 PNG +（可选 BGM） | 同左 + 场景定义 + 逐句字幕 |
| 处理 | 随机抽素材 → trim 随机入点 → 缩放铺满 1080×1920 → 循环补齐到人声总长 → 叠加固定水印 → 混音 → 一次编码 | 场景窗口切分 → 逐场景 filtergraph → 场景 mp4 → 合流 |
| 中间产物 | **无**（直接出 `final.mp4`） | `scenes/scene_00N.mp4` |
| 音画同步 | **不要求**（D2）。视频长度由**人声时长**决定（`-t` 显式指定），跑酷循环补齐 | 同左（二期可选做镜头级对齐） |
| 重试粒度 | **整片重试**（合成失败 ⇒ 重跑，成本可控） | 场景级重试 + 哈希缓存 |
| 水印 | **固定水印（必做）** | 可配多位置/动态水印 |
| 字幕 | **默认开启（Q11 已确认）**，`render.burn_subtitle=true` | 逐字卡拉OK / 多说话人样式 |
| BGM | **默认开启（Q12 已确认）**，且 **BGM 可导入素材库**（`bgm_tracks`）；无素材 ⇒ 静音降级 | 分段 BGM / 侧链避让精细化 |

**保留的工程约束**（虽然不做同步审计，这些仍然是正确性底线，不可省）

1. **CFR 固定帧率**（`fps=30`）：避免 VFR 导致的播放器兼容问题。
2. **显式 `-t` 指定总时长**，**禁用 `-shortest`**：否则视频流先结束会导致画面冻结或提前截断。
3. **音频为时长基准**：`total_ms = voice_master 实测时长`（ffprobe），视频侧用 `-stream_loop` 或 `loop` 滤镜补齐。
4. **`.partial` → 原子改名**：避免崩溃留下"假完成"产物。
5. **随机化仍生效**（P3）：素材随机 + 入点随机 + 微变换 + 编码抖动 —— 这部分**与是否做同步无关**，是防搬运的刚需。

> **被取消的 v3.0 条款**：`av_sync_audit ≤ 80ms` 硬门禁、`repeat_last` 场景扩展（降为二期）、场景级 `render_hash` 缓存（降为二期）、`Σ scene_duration = total_ms` 编译期断言（一期无场景概念）。
> **被保留但降级的 v3.0 条款**：ADR-005（音频为时长真相）**保留**，但"反推镜头区间"的部分**取消**。

#### 0.5.3 新增子系统（D7 + D9）

**① 定时发布调度器**（§06.5.5）

```python
class PublishSchedule(BaseModel):
    """定时发布计划。到点才创建 publish job（不占用 worker 空转）。"""

    schedule_id: str
    task_id: str | None  # None = 仅按计划（如每日固定时段发池中成片）
    platforms: list[str]
    account_ids: list[str]
    mode: Literal["at_time", "daily_window", "interval"]
    at_time: str | None  # '2026-09-14T19:30:00+08:00'
    window: tuple[str, str] | None  # ('18:00','21:30') ⇒ 窗口内随机一个时刻（更自然）
    interval_hours: int | None
    jitter_min: int = 15  # 时刻抖动，避免"每天准点"的机器特征
    enabled: bool = True
    created_by: str
```

- 调度器 = `services/scheduler_service.py`（单进程、30s tick、`next_run_at` 持久化）。
- **不用队列空转**：调度器只负责"到点 ⇒ 创建 `publish` job"，job 本身仍走 §03.4 的原子认领。
- 窗口模式（`daily_window`）默认开启：在窗口内随机取时刻 + `jitter_min`，比固定时刻更自然（R13）。
- 与限频守卫**叠加**：定时 ≠ 免限频（§03.4.4 的 `≤3 条/天/账号` 仍然生效）。
- **策略可编辑（Q14）**：模式 / 窗口 / `jitter_min` / 平台 / 账号 / 启停**全部可在 WebUI 编辑**；编辑 ⇒ **同事务重算 `next_run_at`** + `audit_ops`。

**② 报告子系统**（§06.7）

```python
class ReportSpec(BaseModel):
    period: Literal["daily", "weekly", "monthly"]
    start: str
    end: str
    include: list[Literal["publish", "metrics", "topics", "quality", "cost", "errors"]] = [
        "publish",
        "metrics",
        "topics",
        "quality",
        "cost",
    ]


class Report(BaseModel):
    id: str
    period: str
    start: str
    end: str
    generated_at: str
    summary_md: str  # ★ 人类可读的 Markdown 报告（WebUI 直接渲染 / 可导出）
    data_json: str  # 结构化数据（供图表）
    insights: list[Insight]  # ★ 决策建议（"哪类选题播放最好""哪个时段发布最优"）
    artifacts: list[str]  # 图表 PNG / CSV 路径


class Insight(BaseModel):
    kind: Literal["topic", "timing", "platform", "quality", "cost"]
    statement: str  # '数字型钩子在抖音的完播率高于悬念型 23%'
    evidence: dict  # 支撑数据（可追溯到 publications.metrics_json）
    confidence: Literal["low", "medium", "high"]
    suggested_action: str  # '下轮选题中数字型占比提升至 40%'
```

- 报告**可回灌决策**：`Insight` 经人工确认后写入 `config/persona.yaml` 的偏好项或 `content_directions` 的权重，形成"数据 → 决策 → 选题"闭环。
- 报告生成**不调 LLM**（纯 SQL 聚合 + 规则归因），避免成本与不确定性；`insights[].statement` 由模板渲染。若需自然语言总结，走 §04.1 的 Agent 通道（可选开关）。
- **周期可编辑（Q15）**：由 `report_schedules` 表驱动（§03.3.20），默认 `weekly`（周一 09:00）+ `monthly`（每月 1 日），`daily` 停用；**同周期仅允许 1 个启用**（部分唯一索引）。

## 1. 五条不可动摇的设计原则

| 编号 | 原则（原文 §1.2） | 工程强制手段（不可协商） |
| --- | --- | --- |
| **P1** | **本地优先** | 全链路可断网运行；无 Redis / 无 Docker / 无外部 DB；模型权重与媒资落 `D:` 盘；任意外部服务（LLM/TTS/平台）失效必须有本地降级路径 |
| **P2** | **断点续传** | 唯一续传粒度 = **句子**（配音）+ **场景**（渲染）；产物路径由**内容哈希**决定；任何时刻杀进程，重启后不重复已完成工作 |
| **P3** | **随机防搬运** | 随机化在 **IR 编译前**决策、种子化、落盘可复现；素材受"近 K 任务未使用"约束；成片需过相似度审计门禁 |
| **P4** | **无人工介入** | 全流程无人值守；唯一人工节点是 `awaiting_approval`（**仅 B 级稿件**，A 级自动放行）；其他环节禁止设计人工步骤 |
| **P5** | **确定可审计** | 同输入 + 同 seed ⇒ 同产物；模板版本、提示词版本、引擎版本、随机种子、滤镜图、人工操作全部留痕 |

| `drafting` | 写稿中 | Director 大纲 + Writer 成稿（选题已在选题池完成） |

| `editing` | — | 原文 §2.2⑥ 改稿（同上，≤2 轮） |

| `queued_voice` | 待配音 | 已入队 voice 池 |
| `voicing` | 配音中 | 句级并行推进，可续传 |
| `queued_render` | 待渲染 | 全部句子 `done/skipped` 且时间轴就绪 |

| --- | --- | --- | --- |

## 4. 关键架构决策记录（ADR）

| ADR | 决策 | 理由（要点） | 否决的方案与原因 |
| --- | --- | --- | --- |
| **ADR-001** | 任务池 = **SQLite DB-as-Queue + 租约认领** | 单机零运维、天然持久化、崩溃可恢复、跨进程共享、可 SQL 审计；认领 <1ms | ① `asyncio.Queue`：内存态，重启即丢，无法跨进程，无租约/超时/优先级 ② Celery/rq：需 Redis，Windows 无 prefork，运维成本 >> 收益 |
| **ADR-002** | 进程模型 = **1 API + 1 TTS + 4 Worker（draft/voice/render/publish）** | 崩溃隔离（TTS OOM 不拖垮 WebUI）、依赖隔离（Py3.11/3.12 双 venv）、x264 打满 CPU 不阻塞 API | 单进程全包：一处 OOM 全站不可用；`uvicorn --workers>1`：WS hub 与内存态分裂 |
| **ADR-003** | FFmpeg 调用 = **子进程 argv 数组 + `-filter_complex_script` 文件** | 免 shell 转义、免 Windows 32767 命令行上限、滤镜图可 diff/可 golden/可复现 | ① `ffmpeg-python`（0.2.0，2019 后停更，对复杂滤镜图无实质抽象）② shell 字符串拼接：注入与转义灾难 |
| **ADR-004** | 渲染 = **三层分层编译 + 中间产物哈希缓存** | 单次 filtergraph 规模可控、场景级可重试/可缓存/可并行、错误定位到场景 | 一次到底的超大 filter_complex：不可调试、失败即全量重跑 |
| **ADR-005** | **音频时间轴是唯一真相**（先音频后视频） | 音画不同步的根因是"视频定长再贴音频"；由实测句子时长反推镜头与字幕区间，天然同步 | 先定视频时长再塞音频：必然漂移，只能靠 `-shortest` 掩盖 |
| **ADR-006** | 随机化 = **IR 编译前的种子化 RandomizationPlan** | 结果确定、可复现、可审计、可"再换一版"；所有随机组合走同一编译路径 | 运行时随机（滤镜内随机表达式）：不可复现、无法定位线上事故 |
| **ADR-007** | TTS = **独立 venv（Py3.11 + torch 2.4.0+cu121）+ 常驻 HTTP 推理服务** | 规避依赖冲突；模型常驻避免每句加载；规避 `pynini` 在 Windows 无法安装 | 主 venv 混装：依赖地狱；每句起进程：RTF 不可接受 |
| **ADR-008** | 前端 = **Vue3 + Vite + TS + Pinia** | 操作台状态复杂（看板/日志流/逐句编辑/WS 增量），需要可靠状态层 | 纯 Jinja2：日志流与逐句编辑体验差（保留为降级方案） |
| **ADR-009** | 发布 = **Playwright 浏览器自动化 + 多平台适配器** | 平台开放 API 对个人号不可得；浏览器自动化通用、无需平台授权 | 开放 API（个人号不可得）、第三方 SaaS（违反 P1）、逆向签名（违反平台协议） |
| **ADR-010** | 选题 = **持久化选题池 + 人工勾选（可一键全自动）** | 原文 §2.2② 要求一次 20+ 选题供筛选；选题池可复用、可去重、可统计命中率 | 单任务单稿件：无法批量产出、无法复用选题、无法做去重 |
| **ADR-011** | 发布范围 = **多平台适配器分层**（一线必做 / 二线可选） | 原文未限定平台；国内主流平台差异大（时长/比例/标题/封面/频次） | 单平台硬编码：扩展成本高 |

## 8. DoD（通用完成定义，每个原子任务都必须满足）

1. **契约先行**：实现与对应 `§` 条款一致，并有引用条款编号的测试。
2. **幂等**：同一 job 重复执行结果一致（产物路径由内容哈希决定）。
3. **可观测**：关键路径写 `system_logs`；状态变更写 `task_events`；人工/自动决策写 `audit_ops`；进度可被 WS 消费。
4. **可降级**：每个外部依赖（LLM / TTS / FFmpeg / 磁盘 / GPU / 平台）都有显式失败分支且**有测试覆盖**。
5. **无静默失败**：禁止裸 `except: pass`；所有异常落 `error_code` + 日志 + 状态迁移。
6. **可冷启动复现**：`studio doctor` 全绿 + `pytest -m "not gpu and not slow and not net"` 通过。
7. **超时硬约束**：LLM 单次 120s / 单句 TTS 60s / 一期整片合成 600s（二期单场景 300s）/ 整任务 30min（超时即失败并按策略重试）。
8. **零人工**：除确认闸外，任何任务不得要求人工干预；失败必须能自动重试或自动降级。
